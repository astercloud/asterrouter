# 数据库与事件设计

## 1. 设计范围

本文定义 AsterRouter 本地事实库、AsterCloud 官方服务库、插件私有状态与异步事件的边界。它不是当前所有 DDL 的逐列抄录；具体迁移仍以代码为准，本文规定目标分域、不变量、索引和演进方式。

## 2. 总体原则

1. AsterRouter 与 AsterCloud 使用独立 PostgreSQL，不跨库事务、不跨库外键。
2. PostgreSQL 是业务事实源；Redis、Object Store 和文件目录是协调、内容或资产存储。
3. 财务、状态事件和审计采用追加或版本化更新，不覆盖已生效历史。
4. 所有租户表在 Schema、索引和 Repository 中携带 Scope。
5. 所有至少一次执行的外部副作用都有幂等键、状态、尝试和 Reconcile 信息。
6. 插件不得提交修改 Core 表的 Migration。

## 3. AsterRouter Schema 分域

当前实现以代码内 Repository 建表为主，目标保持逻辑分域并逐步形成显式 Migration Catalog。

### 3.1 安装与身份

| 表族 | 关键字段/约束 | 说明 |
| --- | --- | --- |
| deployment/profile settings | instance、profile、version | 首装事实，单实例唯一 |
| `workspace_users` | normalized identity、status、session_version | 当前用户兼容主表 |
| `auth_identities` | issuer + subject unique | 登录身份绑定 |
| `role_bindings` | principal + scope + role unique | Scope 授权 |
| `departments` | parent、cost_center、path | Enterprise 组织树 |
| `organization_groups` / members | group + member unique | 治理分组 |
| platform tenants/principals | profile + tenant + principal | Platform 数据面主体 |
| API keys | hash unique、fingerprint、principal、lifecycle | Credential 与轮换 |
| external auth integrations | tenant + protocol + issuer/audience | 外部信任配置 |

`workspace_users.balance_micros` 等 Profile 兼容字段不得继续成为通用 IAM 新能力的落点。

### 3.2 供应与路由

| 表族 | 关键约束 |
| --- | --- |
| provider connections | profile + provider name/type，状态索引 |
| provider accounts | provider、secret ciphertext、status、capacity、runtime version |
| provider account models | account + upstream model unique |
| gateway models | profile + public model unique |
| model routes | gateway model + account + upstream model unique |
| routing groups/members | profile + group，成员唯一 |
| health checks | provider/account + checked_at 索引，按保留期分区或清理 |
| risk blocks/circuit state | resource + reason + effective window |

Secret Ciphertext 与 Hint 分离；任何 List Query 不读取或扫描 Secret 列。

### 3.3 执行与任务

| 表族 | 必要约束 |
| --- | --- |
| AI operations | owner + idempotency key unique（非空时）、request fingerprint |
| AI attempts | operation + attempt_number unique、dispatch_key unique |
| AI jobs | operation unique、status_version、queue dimensions |
| job events/progress | job + version unique，按 created_at 索引 |
| delivery/dispatch leases | resource unique、lease_until、token |
| realtime sessions | session ID、owner、attempt、closed state |
| provider callbacks | provider + event_id unique、payload digest |

Operation 与 Job Admission 在一个事务内写入初始事件和 Outbox。Lease Token 不通过公开 API 返回。

### 3.4 Usage、价格与账务

| 表族 | 必要约束 |
| --- | --- |
| usage records | operation + attempt + version unique |
| pricing rules | profile/tenant + purpose + slot unique |
| pricing rule versions | rule + revision unique；每个 rule 最多一个 draft |
| pricing evaluations | usage + purpose + phase/version unique |
| billing holds | operation unique、pricing version snapshot |
| billing ledger entries | operation + attempt + usage_version + purpose unique |
| effective observations | source + subject + observed_at/digest unique |
| cost/savings decisions | operation + decision version unique |

金额使用 `BIGINT micros` 与 currency。规则表达式、Context 和结果保存稳定 JSON Schema 版本与 Digest。

### 3.5 Artifact

| 表族 | 必要约束 |
| --- | --- |
| artifacts | owner、operation、status_version、store key unique（适用时） |
| artifact events | artifact + version unique |
| artifact sink destinations | profile/tenant + name unique，secret ciphertext |
| artifact deliveries | artifact + sink + attempt unique，幂等交付 key |
| artifact access audit | artifact + actor + action + time |

Object Key 推荐结构：`profile/{profile_id}/tenant/{tenant_id}/artifact/{artifact_id}/{variant}`。Key 是定位手段，不替代数据库 ACL。

### 3.6 插件本地事实

当前已有 `plugins`、`plugin_configs`、Catalog Snapshot、Official Package、Package Cache、Installation、Security Advisory、License Snapshot、Plugin API Token 和 Official Feed 表族。

目标约束：

- `plugin_id + version + os + arch + digest` 唯一确定 Package。
- Installation 引用不可变 Package，保存状态和激活版本。
- Config 的 Settings 与 Secret Ciphertext 分离。
- Runtime/Supervisor 瞬时状态可以独立表或内存投影，不覆盖 Installation 事实。
- Package Cache Path 不是信任依据，读取前仍核对 Digest。

### 3.7 审计、Trace 与 Outbox

- Audit 追加写，按 Profile/Tenant、Actor、Resource、CreatedAt 索引。
- Gateway Trace 设置短于 Audit/Ledger 的保留期，敏感正文默认不入库。
- Transactional Outbox 与业务事务同库同事务；`aggregate + event_version` 唯一。
- 投递尝试使用 Lease、Attempt Count、Next Available 和 Dead Letter 状态。

## 4. AsterCloud Schema 分域

AsterCloud 当前使用显式版本迁移，目标继续保持应用域与迁移所有权一致。

### 4.1 Identity

`principals`、password credentials、permission grants/denies、API credentials、refresh sessions、auth events。Principal 类型与角色分离；API Credential 只存 Hash。

### 4.2 Commerce

`customers`、accounts、members、products、plans、SKUs、licenses、license instances、entitlements、official service subscriptions、grants、audit logs 和 idempotency records。

商业不变量：

- SKU 指向版本化产品权利，不直接等同 Plugin Version。
- License 是客户购买/授予的容器，Entitlement 是细粒度权利。
- Grant 有来源、数量、有效期和幂等引用。
- 履约失败可重试，不重复产生权利。

### 4.3 Redemption 与激活

兑换码 Batch、Code、Redemption、Fulfillment Job；Signing Key、Signing Operation、License Activation、Offline License File、Revocation。

- Code 只保存加 Pepper Hash；导出明文使用受控加密封存。
- 单次 Code 通过唯一约束保证一次兑换。
- 激活绑定 License、Instance 与 Fingerprint，解绑/换机有显式状态。

### 4.4 Catalog 与供应链

`plugins`、versions、manifests、compatibilities、packages、catalog snapshots、core releases、security advisories、affected versions 和 package download grants。

- Version 内容发布后不可变。
- Package 保存 Object Key、SHA-256、Size、OS/Arch、Signature 和状态。
- Snapshot 保存单调序号、Payload Digest、签名 Key 和有效窗口。
- Advisory 的影响范围使用规范化版本关系，不只保存自由文本。

### 4.5 Developer Platform

Developer Account、Organization、Plugin Project、Upload Session、Review Request、Review Step、Scan Result。

Upload 完成前 Package 不进入 Catalog；Review Decision 与签名发布分离，二者均审计。

### 4.6 Official Service 与 Intelligence

Official Service、Version、Schema Compatibility、Provider、Endpoint、Probe Node、Probe Task/Request。Probe Result 和 Feed Asset 需要来源、Schema、时间窗、Digest 与发布状态。

## 5. 插件私有数据

首选方案：Host 提供按 `plugin_id` 隔离的 Key-Value/Blob/Job API，Core 负责配额、备份和卸载保留策略。现有复杂 Sidecar 可使用版本独立 `data-dir` 中的 SQLite/文件，但必须满足：

- 路径由 Host 分配，不接受插件任意绝对路径。
- 无 Core 数据库网络权限。
- 数据 Schema 与 Package Version 解耦并提供自身 Migration。
- 更新前备份，失败可回滚，卸载默认保留。
- 导出和 Purge 是显式高风险操作。

## 6. 事件 Envelope

```json
{
  "event_id": "evt_...",
  "event_type": "usage.recorded.v1",
  "aggregate_type": "ai_operation",
  "aggregate_id": "op_...",
  "event_version": 1,
  "occurred_at": "2026-07-22T00:00:00Z",
  "profile_scope": "enterprise",
  "tenant_id": "tenant_...",
  "trace_id": "...",
  "payload": {}
}
```

Payload 不包含 Secret、Key、Prompt/Response 原文。外部 Sink 的字段必须有专门 Schema，不能直接序列化内部数据库对象。

## 7. 事务边界

| 动作 | 同一事务内必须完成 |
| --- | --- |
| Durable Admission | Operation、Job、初始 Event、Hold、Outbox |
| Provider Dispatch Prepare | Attempt、Dispatch Intent、状态版本 |
| Usage Settlement | Usage、Evaluation、Ledger、Hold、Outbox |
| Artifact Transition | Artifact CAS、Artifact Event、Outbox |
| Plugin Install Fact | Package/Installation 状态、Audit；文件激活通过可恢复协调 |
| AsterCloud Fulfillment | Redemption/Order 状态、Grant/License、Worker Job/Audit |

数据库与 Provider/Object Store/File System 不可能形成分布式事务，使用 Staging、状态机、Digest 和 Reconcile 收敛。

## 8. 索引与保留

- 所有外键查询、Lease 领取、状态+时间扫描和 Tenant 列表有对应索引。
- 高写入 Event/Trace/Health 表按时间分区或建立批量保留任务。
- Ledger、License、Grant、Security Advisory 和 Audit 按法规/合同长期保留。
- Prompt/Response 默认不持久化；显式 Debug Capture 有审批、加密和短 TTL。
- 删除任务采用有界 Batch、游标和审计，避免长事务。

## 9. 迁移规范

1. Migration 文件不可修改已发布版本。
2. 每次迁移提供 Up；不可安全 Down 时提供前向修复和恢复说明。
3. 使用 Expand/Backfill/Switch/Contract，跨版本滚动升级期间保持兼容。
4. 高风险 DDL 在生产前以真实规模副本验证锁时间和磁盘增长。
5. 应用启动检查 Schema Version，但不允许多个副本无锁执行迁移。
6. 迁移前自动备份不替代人工核对目标数据库。

## 10. 数据库验收

- Repository Contract Test 同时覆盖 Memory（仅开发）与 PostgreSQL 行为差异。
- Tenant Scope、唯一约束、CAS、Lease 和幂等在并发压测下验证。
- 任一外部副作用前后崩溃都能通过数据库状态 Reconcile。
- 备份恢复后抽样验证 Secret 可用、Ledger 平衡、Job/Outbox 收敛和插件资产一致。
- AsterRouter 与 AsterCloud 无隐式跨库查询、共享表或分布式事务。
