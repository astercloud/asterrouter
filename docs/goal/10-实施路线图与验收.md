# 实施路线图与验收

## 1. 实施原则

1. 先冻结边界和契约，再扩功能与规模。
2. 先保证身份、幂等、计量和恢复正确，再做成本智能化。
3. 每阶段只维护一条主路径；兼容路径有 owner、调用指标和退出条件。
4. 发布以端到端结果验收，不以页面、表或接口“已写完”作为完成。
5. AsterRouter、AsterCloud 与插件可独立发布，但通过兼容矩阵共同验收。

## 2. 当前基线

### 2.1 已具备

- 多 Surface/Profile、身份、Key、Provider、Account、Gateway Model、Route 和治理策略。
- 文本、图片、音频、视频、Realtime、Direct 与 Durable Job 主链路。
- Usage、Pricing、Billing Hold/Ledger、Artifact、Outbox 和 Usage Sink。
- PostgreSQL Repository，Redis 队列/容量/亲和，Local/S3 Artifact。
- 插件 Catalog、签名、Package、安装、License、Feed、前端贡献、Sidecar Supervisor 和 Host API。
- AsterCloud Commerce、Catalog、Developer Review、License Activation、Official Services 和 Provider Intelligence。

### 2.2 主要风险

- 当前功能面很宽，公开契约、状态机和错误码尚未形成单一版本化规范。
- `controlplane` 聚合大量领域，跨域事务与依赖方向需要持续收敛。
- 多实例、故障恢复、插件权限隔离和云端信任链需要系统级验证，而非只靠单元测试。
- 多版 roadmap 并存可能继续产生“已实现/目标态”口径混淆。
- Profile 兼容商业模型与通用 Platform 模型容易互相渗透。

## 3. M0：事实源与契约冻结

目标：停止边界漂移，建立后续开发的共同基线。

### 交付

- 采用本目录作为目标态事实源，历史 roadmap 标注状态与引用关系。
- 发布 Gateway、Management、Plugin Host、Catalog、License、Feed 的协议版本表。
- 固化 `CanonicalAuthContext`、`AIOperation`、`AIAttempt`、`AIJob`、`UsageRecord`、`Artifact` 状态机。
- 为 Core/Plugin/AsterCloud 建立数据归属检查清单和禁止依赖规则。
- 梳理所有 `COMPAT/DEPRECATED` API、表、配置和 UI，记录调用方与退出版本。

### 验收 AC-M0

- `AC-M0-01`：每个公开入口可映射到一个 owner、协议版本、错误模型和测试。
- `AC-M0-02`：文档术语、API 字段和代码核心实体无未解释冲突。
- `AC-M0-03`：新增插件不能直连 Core DB/Redis，静态检查和评审模板覆盖。
- `AC-M0-04`：CI 检查 Markdown 链接、需求 ID 唯一和兼容矩阵格式。

## 4. M1：数据面正确性与公开契约

目标：把现有宽能力收敛为可承诺的稳定数据面。

### 交付

- 文本/图片/音频/视频/Realtime 的兼容矩阵、请求限制、错误码和提交点。
- Direct/Durable 的统一 Auth、Policy、Route、Usage 和 Billing Pipeline。
- 四层幂等、Dispatch Unknown Reconcile、Callback/Poll 竞态和取消语义。
- Artifact ACL、五种 Policy、交付/删除状态和短期访问 URL。
- SDK/cURL 契约样例与 Provider Adapter Conformance Suite。

### 验收 AC-M1

- `AC-M1-01`：所有协议入口通过黑盒契约测试与恶意输入测试。
- `AC-M1-02`：关键外部调用点故障注入后无重复 Provider 任务、Usage 或 Ledger。
- `AC-M1-03`：流式首包后失败不跨 Provider 拼接。
- `AC-M1-04`：Artifact 越权、路径逃逸、超限和删除失败测试通过。
- `AC-M1-05`：任一成功 Operation 的身份、Attempt、Usage、价格和 Trace 关联完整。

## 5. M2：身份、租户与治理收敛

目标：自然人、组织、机器主体与 Credential 分离，统一各 Profile 的权限计算。

### 交付

- 明确 User、Tenant、Membership、Department、Gateway Principal、ServiceAccount 和 API Key 关系。
- 统一 Scope、RoleBinding、显式 Deny、最后管理员保护和离职处理。
- External Auth Integration 的 HMAC/JWT/JWKS、重放保护与降级策略。
- Key Family 轮换、重叠窗口、缓存失效和紧急撤销。
- Simulator 输出最终权限、Route 与 reason code，不泄露 Secret。

### 验收 AC-M2

- `AC-M2-01`：跨 Profile/Tenant/Principal 的 IDOR 和负向权限矩阵全通过。
- `AC-M2-02`：移除自然人不影响 Service Principal；禁用 Principal 立即阻止其所有 Key。
- `AC-M2-03`：外部 Context 重放、过期、受众错误、Key 轮换均 fail closed。
- `AC-M2-04`：最后管理员、恢复账号和高风险审批场景可演练。

## 6. M3：插件平台 GA

目标：让官方与第三方插件可以安全、可预测地开发、审核、安装、运行和撤销。

### 交付

- `plugin-manifest.v1`、Host Envelope、Capability/Permission Registry 和错误码冻结。
- Plugin SDK、示例、Schema 工具、Conformance Test 和本地开发 Host。
- 可复现 Package、Checksum、SBOM、签名、兼容性和权限差异检查。
- 安装/启用/禁用/更新/回滚/卸载状态机与版本化 Active 目录。
- Sidecar 沙箱、资源限制、出站 Allowlist、短期 Token、Supervisor 与运行诊断。
- AsterCloud Developer Upload/Review/Scan/Publish 和安全撤销闭环。

### 验收 AC-M3

- `AC-M3-01`：ImageGen、VideoGen、MonitorPrice、Provider Trust 全部通过同一套契约，无专用 Host 分支。
- `AC-M3-02`：恶意包、签名错误、路径穿越、权限升级和超大响应被阻止。
- `AC-M3-03`：Sidecar 崩溃/超时/资源耗尽不影响 Core 健康和其他插件。
- `AC-M3-04`：更新中断可自动收敛到旧版可用或新版明确失败。
- `AC-M3-05`：安全公告到客户端识别/隔离达到定义的撤销 SLA。

## 7. M4：AsterCloud 信任与商业闭环

目标：在线和离线场景都可获得可信 Catalog、License、Entitlement 与 Feed。

### 交付

- Offline Root、用途分离的在线签名 Key、轮换、撤销和签名审计。
- Catalog Bootstrap/Snapshot、防回滚序号、Package Download Grant。
- 在线激活、离线请求/响应文件、实例解绑/换机和 Grace Policy。
- Product/Plan/SKU/License/Entitlement/Grant/Subscription 的履约一致性。
- Official Service Version、Schema Compatibility、签名/加密 Feed 和本地陈旧度。
- AsterCloud API/Worker HA、Object Store 生命周期、备份和灾备演练。

### 验收 AC-M4

- `AC-M4-01`：断网后在有效窗口内完成 Gateway 和已授权插件回归。
- `AC-M4-02`：过期、撤销、序号回退、未知 Key 和篡改 Snapshot 全部拒绝。
- `AC-M4-03`：兑换/激活/重试不产生重复 License、Grant 或履约 Job。
- `AC-M4-04`：签名 Key 轮换及泄露处置完成演练。
- `AC-M4-05`：AsterCloud 无 Prompt、Response、Provider Secret、Gateway Key 和逐请求 Usage 默认采集路径。

## 8. M5：规模化运行与 FinOps

目标：在多副本、持续负载和复杂供应下保持正确性、可靠性与成本可解释。

### 交付

- API/Worker/Plugin Host 分角色运行，Redis 原子容量、Ready Index 和亲和。
- SLO、OpenTelemetry、业务健康 Dashboard、错误预算与 Runbook。
- Effective Pricing 来源/置信度/TTL、成本约束路由与 Savings Evidence。
- Provider 账单导入、Usage/成本差异对账和手工处置工作流。
- Artifact Store 大对象、客户 Sink、生命周期和存储成本治理。
- PostgreSQL、Redis、Object Store、插件与 Provider 故障演练自动化。

### 验收 AC-M5

- `AC-M5-01`：目标并发下 Route 容量不超卖，租户公平性达到门槛。
- `AC-M5-02`：API/Worker 滚动升级不重复任务或丢失结算。
- `AC-M5-03`：成本优化不突破成功率、延迟、信任和预算硬约束。
- `AC-M5-04`：Savings Evidence 与 Provider Bill 可抽样回溯到 Operation。
- `AC-M5-05`：恢复演练满足 RPO/RTO 目标。

## 9. M6：多 Region（条件阶段）

只有单 Region HA、幂等、配置版本、账务对账和恢复演练稳定后才进入。

### 交付

- 标准 Region Cell、全球/固定域名、Tenant Allowed Region 与数据驻留。
- 配置 Snapshot 发布、Region ACK、最后有效配置和安全撤销快速通道。
- 异步任务 `home_region`、跨区接管租约和 Artifact 数据位置。
- Usage Event 汇聚与 Region 隔离时的预算 Lease。
- Region 故障切流、回切、数据恢复和客户沟通流程。

### 验收 AC-M6

- `AC-M6-01`：禁止跨区客户在任何故障下都不发生隐式越区。
- `AC-M6-02`：允许跨区的请求在目标 RTO 内恢复，无重复任务/账务。
- `AC-M6-03`：配置版本、Key 撤销和 Tenant 冻结在目标窗口内全区生效。

## 10. 发布门槛

每个里程碑必须同时通过：

- 功能：需求、主流程、异常流和兼容测试。
- 正确性：并发、幂等、状态机、结算和恢复。
- 安全：隔离、Secret、供应链、权限与审计。
- 性能：基线、目标负载、资源预算和退化曲线。
- 运维：指标、告警、Runbook、备份、回滚和故障注入。
- 文档：用户、API、升级、迁移、已知限制和本目标文档同步。

任何 P0 数据损坏、跨租户、Secret 泄露、重复扣费、不可回滚迁移或无恢复方案的问题都阻止发布。

## 11. 需求追踪

```text
Goal -> FR/NFR -> Use Case -> Design/ADR -> Code/Test -> Acceptance -> Release Evidence
```

发布证据应保存版本、Commit、环境、测试结果、性能基线、漏洞例外、迁移演练和审批。验收项不能只链接人工截图。
