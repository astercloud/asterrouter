# 账号体系设计

## 1. 设计结论

账号体系分为四层：登录身份、组织/租户上下文、业务 Principal 和 Credential。四层不得继续压在一个 User 或 Token 上。

```text
Human Identity -> User -> Membership/RoleBinding -> Tenant/Profile
Machine Identity -> Gateway Principal/ServiceAccount -> API Key
External Platform -> Integration -> Signed Context -> External Principal Reference
```

## 2. 当前模型与收敛方向

| 当前实体 | 当前用途 | 目标定位 |
| --- | --- | --- |
| `workspace_users` | 登录、角色、部门、余额和限制的混合载体 | `COMPAT`，逐步拆出组织与机器身份责任 |
| `auth_identities` | 登录身份 | 保留，成为 User 与认证源的绑定 |
| `role_bindings` | Scope 权限 | 保留并统一 Profile/Tenant/Resource Scope |
| `api_keys` | 多类型 Gateway Key | 保留，明确其为 Credential 而非主体 |
| `platform_tenants` | Platform 客户边界 | 保留，不复用 Relay Customer 表 |
| `gateway_principals` | Platform 机器/集成主体 | 扩展为统一机器主体模型的目标基础 |
| Relay Customer/Wallet | Relay 商业与余额 | Profile 内兼容，不提升为通用 IAM |

## 3. 登录身份

### 3.1 User

User 表示可登录 AsterRouter 管理面的自然人，包含稳定 ID、显示信息、状态与安全版本，不持有生产工作负载所有权。

### 3.2 Identity

| 类型 | 唯一键 | 要求 |
| --- | --- | --- |
| Password | 本地规范化用户名/邮箱 | Argon2id/bcrypt、重置 Token Hash、MFA 策略 |
| OIDC | Issuer + Subject | Audience、Nonce、PKCE、Issuer 白名单 |
| Recovery | 本地恢复主体 | 离线保存、强 MFA、全部操作审计 |

一个 User 可绑定多个 Identity；同一外部 Identity 只能绑定一个 User。邮箱不是跨 IdP 的全局身份键。

## 4. Profile、Tenant 与 Membership

- `Profile` 是实例部署角色，不是客户组织。
- `Tenant` 是数据和权限隔离边界，可在 Enterprise/Platform 等需要的 Profile 中存在。
- `Membership` 连接 User 与 Tenant，包含状态、角色和有效期。
- `RoleBinding` 支持 Profile、Tenant 和资源级 Scope；Membership 可作为常用绑定的产品投影。

目标约束：一个 User 可加入多个 Tenant，但每次 UI/API 请求必须明确当前 Tenant；切换上下文不沿用上一 Tenant 的缓存授权。

## 5. Principal

| Principal 类型 | 用途 | 生命周期 Owner |
| --- | --- | --- |
| Human | 管理面或个人调用 | User/管理员 |
| Service | 生产服务、自动化、CI | 应用 Owner |
| Developer | Platform 客户开发者/项目 | Tenant 管理员 |
| Integration | 外部业务平台或系统集成 | 平台集成管理员 |

Principal 有 Active/Disabled 状态、Tenant、显示名和元数据。禁用 Principal 是集中撤销点，必须覆盖所有 Key、短期 Context 和新任务。

## 6. API Key

### 6.1 Key 内容

服务端记录至少包含：

- ID、Name、Hash、Fingerprint、Prefix、Status。
- Profile/Tenant/Principal/Customer 归属。
- Scopes、Model Allowlist、Modality/Operation Allowlist。
- QPS/RPM/TPM/Concurrency、Token/预算/媒体限额。
- CIDR、Lane Policy、Artifact Policy/Sink。
- Rotation Family、Replaces/ReplacedBy、Retire/Expires/LastUsed 时间。

### 6.2 Secret 格式

Key 使用带环境/产品前缀和足够随机熵的格式。服务端只保存抗离线猜测的 Hash 与用于查找/展示的 Prefix/Fingerprint。完整 Secret 仅创建/轮换响应一次，不能通过管理 API 再取回。

### 6.3 轮换

```text
old active -> old retiring + new active -> overlap deadline -> old retired
```

- 重叠窗口有上限并可设为零。
- 新旧 Key 属于同一 Rotation Family，分别审计 Usage。
- 紧急撤销跳过窗口，立即 Disabled。
- UI 提供最近使用时间，帮助确认旧 Key 已退出。

## 7. External Auth

External Auth Integration 包含 Tenant、协议、Issuer/Audience、Secret/JWKS、允许 Scope 上限、状态和轮换信息。

外部 Context 至少声明：

- integration/tenant、subject reference、principal type/reference；
- issued_at、expires_at、nonce/jti、audience；
- 请求允许的 scopes、models、operations 和业务维度；
- 可选 entitlement reference，不能突破 Core Policy 硬限制。

AsterRouter 不保存外部登录 Session 或刷新 Token。必要时只保存不可逆 Subject Reference 和审计摘要。

## 8. 权限角色

建议预置角色：

| 角色 | 范围 | 主要权限 |
| --- | --- | --- |
| System Administrator | Instance | 恢复、升级、根配置、License |
| Security Administrator | Instance/Profile | 身份、MFA、审计、插件权限 |
| AI Platform Administrator | Profile/Tenant | Provider、Model、Route、Policy |
| FinOps Administrator | Profile/Tenant | 价格、成本、预算、账务与报表 |
| Plugin Administrator | Profile | 安装、配置、启停和诊断插件 |
| Tenant Administrator | Tenant | 成员、Principal、Key、Policy |
| Developer | Tenant/Project | 创建受限 Key、调用与查看自身 Usage |
| Auditor | Scope | 只读审计与合规证据 |

权限使用细粒度 Action Registry 实现，角色只是权限集合。显式 Deny 与系统安全守卫优先。

## 9. 高风险保护

- 不能删除或降级最后一个有效 System Administrator。
- 修改自身高权限、关闭 MFA、恢复备份、导出审计和安装高权限插件需要重新认证。
- 批量禁用 Principal/Key 先显示影响的活跃应用、Job 和最近调用。
- Break-glass 账号默认禁用在线登录或使用硬件 MFA，启用即告警。
- 管理员不能回显自己无业务需要的 Provider Secret。

## 10. 生命周期

### 10.1 员工离职

1. 禁用 User 与 Identity，撤销 Session。
2. Personal/User Key 立即禁用或转移审批。
3. Service Principal 与其 Key 保持，由新的 Owner 管理。
4. 转移审批、未完成任务和资源所有权。
5. 保留审计，不复用旧 User ID。

### 10.2 Tenant 冻结

- 阻止新 Gateway Operation、Key 创建和管理写操作。
- 已执行任务按策略取消或完成，不能产生无界新成本。
- Usage、账单、Artifact 导出和审计保留受控只读路径。
- 解冻产生新版本和审计，不能删除冻结历史。

### 10.3 实例恢复

恢复后验证 Instance ID、Secret Key、License Binding、Session Version 和插件 Token。无法证明安全的 Session/Token 全部失效，业务事实不丢失。

## 11. 迁移策略

1. 为现有 Workspace User/Key 补稳定 Principal 引用。
2. 将个人生产 Key 标记并提供 Service Principal 转换工具。
3. 双读期间以新 Principal/Scope 为授权事实，旧字段仅输出兼容。
4. 统计无新归属的调用并通知 owner。
5. 禁止创建旧形态后，再删除兼容写与字段。

迁移不得通过复制 Key 明文完成；只能重绑定 Hash 记录或要求轮换。

## 12. 验收不变量

- 同一 User 在不同 Tenant 的权限和缓存完全隔离。
- User 删除/禁用不会删除 Usage、Audit、Ledger 和 Service Principal。
- Principal 禁用后所有 Credential 和外部 Context 均不能创建新 Operation。
- Key 明文无法通过数据库、API、日志、备份和诊断恢复。
- 最后管理员、Break-glass、离职、Tenant 冻结和恢复流程均有自动化测试。
