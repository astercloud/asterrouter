# 体验架构与信息架构

## 1. 设计目标

V1 信息架构暂不按数据库表、进程角色或 Profile 展开，而按用户每天要回答的五个问题组织：

1. 今天是否有事情必须处理？
2. 哪些应用正在使用 AI？
3. 团队可以使用哪些模型？
4. 使用了多少、花了多少？
5. 谁可以管理和使用？

内部对象仍保持准确边界。信息架构只改变发现路径和组合方式，不改变事实所有权。这五个问题是待任务测试验证的基线，不是固定入口数量指标。

## 2. 一个管理入口

实例管理员、平台工程师和业务负责人进入同一个 AsterRouter 管理入口。系统依据权限与实例意图显示能力，不再要求用户在 `/admin`、`/console`、`/operator`、`/platform` 之间选择产品。

```text
AsterRouter
├── 今天
├── 应用
├── 模型
├── 用量
├── 团队
├── 工具（有可用工作台时出现）
└── 管理员菜单
    ├── 高级治理
    ├── 诊断
    ├── 扩展管理
    ├── 审计
    └── 系统设置
```

导航展示规则：

- 无权限的入口不显示，不展示不可点击的菜单制造噪声。
- “工具”没有可用项时不出现；有一个工具时直接显示工具名称，有多个时显示工具列表。
- “团队”在个人实例可简化为“成员与访问”，但路由和信息模型保持一致。
- 高级治理和诊断可以被全局搜索命中，但不占一级导航。
- 专业角色可以固定诊断、SLO 或 FinOps 视图；固定入口不改变统一路由和权限模型。
- 管理入口统一不等于权限统一；服务端仍对每次请求执行 Scope、Tenant 和 Role 校验。

## 3. 三级体验架构

### 3.1 L1：结果层

服务日常任务，使用业务语言，默认不出现内部 ID。

| 入口 | 默认内容 | 主要动作 |
| --- | --- | --- |
| 今天 | 待处理事项、运行结论、最近变化 | 处理事项、继续接入 |
| 应用 | 应用、客户或外部系统及其访问状态 | 新建应用、发放/轮换凭据 |
| 模型 | 已发布模型、模型来源和供应健康 | 发布模型、增加备用来源 |
| 用量 | 调用、费用、预算和趋势 | 定位异常、调整预算 |
| 团队 | 成员、服务身份和权限 | 邀请成员、调整角色 |

### 3.2 L2：治理层

从一个 L1 对象的“管理”或“高级设置”进入，回答“为什么这样运行”和“如何改变规则”。

| 上下文 | 治理内容 |
| --- | --- |
| 应用 | Scope、Policy、预算、Credential 生命周期、数据保留 |
| 模型 | 来源优先级、容量、Route 条件、价格与能力映射 |
| 用量 | 定价、成本分摊、Usage Sink、导出、账务规则 |
| 团队 | 角色绑定、组织组、部门、职责分离 |
| 工具 | 权限、配置、数据范围、资源限制 |

L2 必须保留当前对象上下文和返回路径，不能把用户扔进无关的全局表格。

### 3.3 L3：诊断层

供平台工程师和 SRE 使用，允许精确展示工程术语：Provider Account、Route、Attempt、Trace、Job Event、Artifact、Plugin Runtime、Audit Event。

L3 的入口有三种：

- 从异常事项打开，自动带入时间、应用、模型和 request ID 过滤条件；
- 从应用、模型或活动详情打开；
- 管理员通过全局搜索或管理员菜单直接进入。

诊断层默认只读。会改变生产行为的动作必须回到所属 L2 对象执行，避免同一事实出现两个修改入口。

## 4. 主导航规格

### 4.1 今天

“今天”不是 Dashboard 集合，而是系统对当前状态的判断。页面信息顺序固定：

1. 结论：正常、需要关注或正在受影响；
2. 需要用户处理的事项；
3. 未完成的首次接入或迁移任务；
4. 最近发生的关键变化；
5. 简短运行摘要。

正常时页面应短。资源数量和趋势不用于填满页面，但必须提供监控覆盖、数据新鲜度、关键 SLO 和完整观测入口。数据缺失时显示“状态待确认”，不把未知解释为正常。

### 4.2 应用

“应用”统一承载谁在调用 AsterRouter：

- 团队网关：内部应用、脚本、自动化 Agent 和个人开发环境；
- 服务网关：客户、外部 Tenant、合作方系统和内部服务；
- 凭据不是一级对象，而是应用的访问方式；
- Policy 和预算不是全局列表优先，而是应用的治理属性。

列表默认按“最近使用”和“需要关注”排序，不按创建时间机械排序。

### 4.3 模型

“模型”区分两个自然概念：

- **已发布模型**：应用看得见、可以请求的稳定名称；
- **模型来源**：AsterRouter 从哪里获得供应。

Provider Connection、Provider Account、Route 与 Routing Group 放在模型详情的“供应”中。默认只展示供应是否健康、是否有备用来源和当前影响；内部拓扑按需展开。

### 4.4 用量

用量默认回答：谁在用、用了什么、花了多少、是否偏离预期。第一组维度固定为应用与模型，Provider、Account、Route 作为诊断维度放在高级筛选。

费用、成本和客户计费必须清楚区分：

- 成本：上游供应带来的支出；
- 内部费用：分摊给团队或项目的金额；
- 客户费用：服务网关向客户计费的金额。

不得用一个“金额”字段混合三种口径。

### 4.5 团队

团队页组合成员、Service Identity 和权限结果。部门、组织组、RoleBinding 是高级组织方式，只在规模或权限需要时出现。

## 5. 两种意图的条件架构

### 5.1 团队网关

默认结构即五项主导航。Personal 与 Enterprise 的差异通过能力和权限体现，不改变产品词汇：

| 条件 | 体验变化 |
| --- | --- |
| 单人使用 | 隐藏邀请、部门和复杂授权 |
| 多成员 | 显示团队、角色和应用负责人 |
| 启用成本治理 | 用量出现预算与成本分摊 |
| 启用高可用 | 模型供应出现容量与实例健康 |

### 5.2 服务网关

仍使用同一主导航，只增加上下文标签：

| 入口 | 已有业务系统 | AsterRouter 管理客户 |
| --- | --- | --- |
| 应用 | Tenant、集成、访问凭据 | 客户、客户组、访问凭据 |
| 用量 | Usage Sink、交付状态 | 套餐、余额、定价、账单 |
| 团队 | 平台成员与服务身份 | 运营成员与服务身份 |
| 今天 | 集成/交付异常 | 余额、风险、通知和供应异常 |

“客户”和“Tenant”是应用页的条件视图，不再创建与模型、Provider、Trace 重复的整套后台。

### 5.3 委托用户入口

Customer/Portal 是受限角色的委托入口，不是第五种管理产品。它保持轻量独立 Shell：

```text
概览 | 接入 | 用量 | 账单（可选） | 账户
```

委托用户不看到模型来源、Route、全局费用和其他 Tenant。相同事实由统一 Application、Credential、Usage API 按权限投影，不复制业务逻辑。

## 6. 当前对象到目标入口

| 当前对象 | 默认入口 | 高级位置 |
| --- | --- | --- |
| Profile | Setup 使用意图 | 系统设置 / 部署信息 |
| Provider Connection | 模型 / 模型来源 | 模型来源详情 |
| Provider Account | 模型详情 / 供应 | 诊断 / Provider Account |
| Gateway Model | 模型 / 已发布模型 | 模型详情 |
| Model Route、Routing Group | 模型详情 / 供应 | 高级选择规则 |
| Principal、API Key | 应用 / 访问 | 高级权限与凭据历史 |
| Policy | 应用 / 权限摘要 | 高级权限 |
| Usage、Cost、Ledger | 用量 | 计费与账务治理 |
| Trace、Attempt | 活动详情 | 诊断 / Trace |
| Job、Artifact | 应用或工具的活动 | 诊断 / Job、Artifact |
| Alert、Risk、Expiry | 今天 / 待处理事项 | 诊断来源 |
| Plugin Installation | 管理员 / 扩展管理 | Runtime 诊断 |
| Plugin Contribution | 真实工具名或所属对象 | 扩展来源与权限 |
| AsterCloud 状态 | 相关更新/授权/安全事项 | 系统设置 / 官方服务 |

## 7. 全局搜索与深链

全局搜索用于到达对象，不承担创建或批量管理：

- 可搜索应用、模型、客户、成员、request ID 和文档化错误码；
- 结果显示所属层级与访问权限，不泄露无权对象是否存在；
- 搜索 Provider Account 或 Route 时直接进入 L3；
- 深链必须保留实例、Tenant、时间范围和返回上下文；
- 无权访问返回明确权限状态，不用 404 掩盖可恢复的角色配置错误；安全策略要求隐藏存在性时除外。

## 8. AI 辅助入口

AI 辅助入口建立在既有信息架构和 Product Facade 之上，不另建一套隐式权限与命令系统。

适合的任务：

- “订单助手昨天为什么变慢了？”等跨 Trace、Route 和 Provider 的只读解释；
- 根据当前应用生成最小 Policy 草案；
- 汇总一次故障的影响、时间线和候选动作；
- 把自然语言转换为可见、可编辑的筛选条件。

交互约束：

- 回答标明数据范围、新鲜度、来源链接和未知项；
- 建议动作转换为类型化命令草案，展示差异和预计影响；
- 修改权限、账务、凭据、Route 和数据流前重新鉴权并明确确认；
- 用户可以不使用 AI 完成所有核心任务；
- AI 不可用时，搜索、表单、诊断和 Runbook 路径保持完整。

## 9. 响应式与可访问性

- 桌面端使用固定主导航与上下文页签；移动端主导航收进菜单，但核心动作不藏入二级菜单。
- 表格在窄屏转为重点字段列表，不做无法操作的横向压缩。
- 状态不只依赖颜色；每个状态有文字、图标和可访问名称。
- 键盘可以完成导航、筛选、对话框确认和凭据复制。
- 动态更新不抢焦点；Attention Item 的新数量通过适度的 live region 通知。

## 10. 信息架构验收

- 任一日常任务最多经过一个主导航和一个对象详情。
- 普通用户无需进入 L3 完成接入、轮换、预算和故障建议动作。
- 同一事实只有一个主要修改入口。
- 两种使用意图共享核心词汇和组件，不维护两套模型管理页面。
- 没有工具、客户计费或高级组织能力的实例不显示空入口。
- 旧 Profile 和路由差异不会泄露为首日选择负担。
- 高频任务可发现性支持五项导航假设；若不支持，按证据调整，不以入口数量否决变化。
- 专业角色无需牺牲精确观测和批量效率来换取普通路径简单。
- 关闭 AI 辅助后，所有核心任务仍可通过确定性界面完成。
