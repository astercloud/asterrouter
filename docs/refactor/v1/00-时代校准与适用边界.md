# 时代校准与适用边界

## 1. 为什么需要这篇文档

本次重构借鉴的张小龙产品观点主要形成于 2010-2012 年。它们来自移动互联网早期的真实产品观察，适合帮助团队识别功能堆叠、界面噪声和用户认知负担，但不能直接作为 2026 年企业 AI 基础设施的规格。

这份材料的正确用法是：

> 借用判断问题的方法，不照搬当年的产品答案。

V1 因此不是“模仿微信式产品”，也不把个人观点当作权威。所有设计结论都必须接受 AsterRouter 用户研究、运行数据、安全边界和工程事实验证。

## 2. 哪些时代前提已经变化

| 2010-2012 年的主要环境 | 2026 年 AsterRouter 的环境 | 设计影响 |
| --- | --- | --- |
| 个人移动应用快速普及 | 多角色共同治理的企业 AI 基础设施 | 不能只为单一普通用户隐藏复杂度 |
| 功能由确定性代码执行 | AI 模型、Agent 和供应行为具有不确定性 | 推荐和自动化必须带证据、置信度与回退 |
| 单设备、短任务、用完即走 | 长期运行的数据面、异步 Job 和账务状态 | 产品目标是“配置后可信运行”，不是简单退出 |
| App 自身形成相对封闭体验 | Provider、AsterCloud、插件和外部系统共同构成生态 | 统一体验必须建立在公开边界和兼容契约上 |
| 推送仍是稀缺的新能力 | 用户面对通知、告警和安全信息过载 | 推送必须按影响、动作和时效严格收敛 |
| 用户数据与云服务边界较简单 | 数据驻留、Tenant、合规、离线与供应链安全成为基础要求 | “方便”不能越过本地自治和授权边界 |
| 说明书通常用于补救消费产品流程 | API、部署、合规和故障恢复依赖精确专业文档 | 首次体验自解释与高质量文档必须同时成立 |

## 3. 保留什么，修正什么

| 原始倾向 | 仍然有效的内核 | V1 的现代化表达 |
| --- | --- | --- |
| 用户不为功能清单付费 | 用户购买结果 | 从“对象是否创建”转向“调用是否可信完成” |
| 需要说明书的产品不是好产品 | 主路径不应靠教程补救 | 首日闭环自解释；高级任务提供完整参考与 Runbook |
| 简单、自然 | 减少无意义选择 | 安全默认、渐进揭示、专业深度完整 |
| 正常状态安静 | 不制造虚假工作 | 不主动打扰，但状态、SLO 和证据随时可验证 |
| 推送让环境触发行动 | 系统应在需要时找到用户 | 只有明确影响、时限和动作的事项才通知 |
| 用完即走 | 不绑架用户注意力 | 配置后可信运行，异常时再介入，即 `set and trust` |
| 一个产品不能多人一起画 | 产品需要统一语言和秩序 | 插件使用受控 Contribution，不依赖个人审美独裁 |
| 默认值就是产品判断 | 系统应承担可推导决策 | 默认值安全、可解释、可撤销，并标明依据 |
| 功能应该藏起来 | 用户不必先懂内部实现 | 内部事实不删除，按结果、治理、诊断分层呈现 |

## 4. 不能照搬的结论

### 4.1 “不需要文档”不能成为目标

首次连接模型和应用应当不依赖外部说明书，这是界面质量指标，不是取消文档的理由。

AsterRouter 必须同时提供四类内容：

1. **界面内解释**：当前结果、影响和下一步；
2. **任务指南**：部署、接入、轮换、恢复等端到端流程；
3. **精确参考**：API、配置、权限、状态机和兼容矩阵；
4. **生产 Runbook**：故障、备份、升级、回滚和安全事件。

高级用户需要文档不是产品失败。真正的失败是界面、文档和真实行为互相矛盾。

### 4.2 “隐藏复杂度”不能隐藏控制权

企业基础设施的用户需要知道：系统依据什么做出 Route、Policy、费用和风险判断，何时发生过自动切换，如何复核和撤销。

V1 隐藏的是不必要的前置学习，不是：

- 安全和账务事实；
- 模型供应差异；
- 自动化依据和副作用；
- Tenant、Scope 与数据边界；
- 精确排障入口。

### 4.3 “安静”不能等于不可观测

首页可以不展示大量 Dashboard，但必须让用户确认监控是否完整、数据是否新鲜、关键 SLO 是否处于正常范围。数据缺失时不能显示“一切正常”。

SRE 和平台工程师可以固定诊断入口、保存视图和订阅 SLO，而不必每天从普通用户首页进入。

### 4.4 “入口少”不能成为审美指标

五项主导航是当前工作假设，不是不可变原则。如果任务测试证明用户无法找到高频能力，应该调整分组、命名或入口数量，而不是要求用户适应设计。

入口数量本身不作为 KPI。衡量的是任务可发现性、完成率、错误率和权限清晰度。

### 4.5 “统一产品声音”不能变成个人独裁

统一来自产品基因、术语、Design Token、Contribution Contract 和评审机制，而不是某一个人的偏好。安全、可访问性和用户证据可以否决纯审美判断。

## 5. 2026 年的产品原则

### 5.1 表面克制，内核透明

普通路径只显示完成任务所需的信息；治理和诊断保留完整事实。任何自动化决定都能追溯输入、规则、执行结果和审计记录。

### 5.2 默认简单，默认值可解释

系统可以推荐模型、Route、Scope 和预算，但必须说明依据。低风险设置可以自动应用；影响安全、费用、数据流和可用性的设置需要确认。

### 5.3 正常安静，状态可验证

没有需要行动的事项时不制造通知。用户仍能查看健康覆盖、数据新鲜度、SLO、最近自动动作和底层证据。

### 5.4 文档与产品使用同一事实

API Schema、配置定义、错误目录、Compatibility Record 和 UI 状态尽量从同一契约生成或校验，减少文档和实现漂移。

### 5.5 AI 辅助，但不替代确定性界面

AI 可以：

- 把自然语言问题转换为受权限约束的查询；
- 解释错误、费用变化和供应差异；
- 草拟 Policy、Route 或修复计划；
- 汇总 Trace、Job 和 Attention 证据。

AI 不可以：

- 成为完成核心任务的唯一入口；
- 绕过 Scope、确认、幂等和审计；
- 在没有证据时宣称系统正常或故障已恢复；
- 自动执行撤销 Credential、修改账务、扩大权限等高风险动作；
- 用流畅文案掩盖未知、冲突和数据陈旧。

所有 AI 建议都应落为类型化命令草案，展示差异、依据、风险和预计影响，再由 Core 按确定性规则验证。

### 5.6 生态开放，主产品仍有秩序

插件可以增加工具、Adapter 和数据服务，但不能自行改变全局导航、权限语义和安全边界。统一体验依靠 Contribution Contract，不把生态能力硬编码回 Core。

## 6. V1 的设计假设

以下是需要验证的假设，不是先验真理：

| 假设 | 预期收益 | 推翻或修正的证据 |
| --- | --- | --- |
| 五项主导航覆盖日常管理 | 降低跨 Profile 和对象查找成本 | 高频任务可发现率下降、用户持续依赖搜索或旧入口 |
| 两种使用意图足以完成默认 Setup | 降低 Profile 认知负担 | 大量实例无法无歧义映射或安装后频繁改模式 |
| Application 能自然组合 Principal、Key 和 Policy | 从调用者视角统一管理 | 共享 Key、多 Principal 或复杂委托场景产生错误归属 |
| PublishedModel 能自然组合 Model、Route 和 Supply | 从应用可见模型出发治理 | 用户主要任务仍必须跨多个供应列表完成 |
| “今天”应以 Attention 驱动 | 减少日常巡检 | 漏报、误报或用户无法建立系统信任 |
| 首日闭环可在十分钟左右完成 | 快速到达真实价值 | 合法网络、合规或供应配置普遍无法达到，应按场景分层 |
| AI 助手能降低高级诊断成本 | 减少日志解释和查询负担 | 建议不可复核、误导率高或用户更慢完成任务 |

每项假设必须有指标、用户测试和复审时间。不能因为已经写入文档或实现就自动变成永久架构。

## 7. 面向不同专业深度

V1 不假设所有用户都希望“越简单越好”：

| 用户 | 默认体验 | 必须保留的专业能力 |
| --- | --- | --- |
| 首次接入者 | 引导完成首次受治理调用 | 可随时查看示例和任务文档 |
| 应用负责人 | 应用、模型、预算和活动 | 精确失败原因与 request ID |
| 平台管理员 | 治理摘要与影响 | Policy、Route、批量操作和审计 |
| SRE | 异常、SLO 和诊断 | 保存视图、Trace、Attempt、Job Event |
| FinOps | 用量、成本和预算 | 定价版本、未知成本、Ledger 证据 |
| 安全/合规 | 权限和风险事项 | 数据流、职责分离、不可变审计与导出 |
| 插件管理员 | 工具结果与扩展管理 | Digest、Permission、Runtime 和撤销 |

简单体验通过分层实现，不通过削弱专业用户实现。

## 8. 决策检查表

每个重大产品决定必须回答：

1. 它解决哪个用户在什么环境中的问题？
2. 这是长期产品基因，还是当前可被推翻的设计假设？
3. 用户少理解了什么，是否也失去了必要控制权？
4. 默认值的依据、风险和撤销方式是什么？
5. 正常状态如何证明可信，异常状态如何提供证据？
6. AI、AsterCloud 或插件不可用时，确定性退路是什么？
7. 哪些数据可以证明这个决定有效或应该废弃？
