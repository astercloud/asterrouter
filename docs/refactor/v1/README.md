# AsterRouter V1 产品体验重构

## 1. 一句话结论

> AsterRouter 不应该先让用户学习一套路由系统，而应该让用户尽快为团队建立一个可信的 AI 入口。

现有 AsterRouter 已经具备完整的数据面、供应管理、身份治理、计量、异步任务、产物和插件能力。V1 重构不再增加能力宽度，重点是让系统承担不必要的操作复杂度，同时让安全、费用、自动化依据和诊断证据始终可验证。

## 2. 重构后的产品承诺

**对使用者：**

> 只接入一次，就能放心使用团队需要的 AI 模型。

“放心”包含四层确定性：

1. Provider Secret 不进入业务应用。
2. Provider 故障、账号容量和模型切换由 AsterRouter 处理。
3. 每个应用只能使用被允许的模型、额度和数据策略。
4. 每次调用、费用和异常都能解释。

这四层由 Core 实现，但不作为首页功能清单展示。

“放心”不等于系统替用户做所有决定。涉及权限扩大、数据外发、费用规则和生产可用性的动作仍需明确确认，并提供依据、影响和撤销方式。

### 2.1 方法来源与时代校准

本方案借鉴张小龙早期关于结果、自然、克制和环境触发的产品判断，但不复刻十多年前移动应用的答案。企业 AI 基础设施还必须满足可解释、可观测、可审计、专业文档、开放生态和 AI 自动化安全。

具体适用边界见 [时代校准与适用边界](./00-时代校准与适用边界.md)。本目录中的导航数量、十分钟目标和聚合对象均为待验证设计假设，不是不可推翻的教条。

## 3. 当前产品问题

当前系统按照工程对象组织：Profile、Provider、Provider Account、Gateway Model、Model Route、Routing Group、Policy、API Key、Trace、Job、Artifact、Plugin。每个对象都合理，但用户必须先理解对象之间的关系，才能完成第一次调用。

结果是：

- 系统能力越完整，首次使用越像部署基础设施。
- 首页展示系统拥有多少资源，而不是用户是否已经可以安全调用 AI。
- 异常存在于多个列表和看板中，需要用户主动巡检。
- 四个 Profile 在首次安装时成为产品选择，而不是内部部署预设。
- 插件以系统扩展概念出现，而不是以用户需要的工作台和能力出现。

## 4. V1 的唯一核心闭环

```mermaid
flowchart LR
  A[连接模型来源] --> B[发布一个模型]
  B --> C[连接一个应用]
  C --> D[完成首次调用]
  D --> E[系统持续守护]
  E -->|只在需要判断时| F[通知用户处理]
  F --> E
```

系统的第一价值时刻不是“创建 Provider 成功”，也不是“Route 已保存”，而是：

> 你的应用已经通过 AsterRouter 成功调用模型；密钥、路由、额度和调用记录均已受保护。

## 5. 重构范围

### 5.1 重构

- 产品定位与面向用户的语言。
- 首次安装、首次接入和第一次成功调用。
- 导航、首页、资源详情和异常处理入口。
- Profile 的产品呈现方式。
- Provider、Route、Key、Policy 等对象在产品层的组合。
- 插件与 AsterCloud 在用户体验中的出现时机。
- 支撑新体验的聚合查询、命令 API 和只读投影。

### 5.2 保留

- Gateway API 与公开协议兼容性。
- Provider、Account、Gateway Model、Route 和 Scheduler 的 Core 模型。
- Auth Context、Policy、Usage、Billing、Job、Artifact 和 Audit 不变量。
- AsterCloud 可选、离线自治和插件安全边界。
- 四个现有 Profile 的持久数据与后端 Scope，作为兼容层继续存在。

### 5.3 不做

- 不重写已经稳定的数据面。
- 不把所有后台能力合并成一张巨型表或一个巨型 Service。
- 不用聊天机器人替代清晰的信息架构。
- 不为了“更简单”隐藏安全、账务或故障事实。
- 不在本轮新增 Provider、协议、插件类型、市场交易或多 Region 能力。
- 不用新旧 UI 长期双轨；兼容入口必须有移除版本。

## 6. 核心产品原则

1. **用户先做事，系统再解释。** 首屏给下一步，不给架构图。
2. **默认值承担产品责任。** 能可靠推导的，不要求用户选择；默认值必须说明依据并可撤销。
3. **渐进揭示。** 普通路径只显示业务概念，内部对象放到高级治理。
4. **异常驱动、状态可验。** 正常状态尽量安静，但健康、SLO、新鲜度和证据随时可查。
5. **结果胜过功能。** 文案表达“你的应用可以调用了”，不表达“已创建六个对象”。
6. **一个概念只出现一次。** 同一事实不在多个菜单中重复管理。
7. **产品表面统一，内核边界清晰。** 简单体验不能破坏 Core 正确性。
8. **克制扩张。** 新功能必须进入核心闭环，否则默认不做。
9. **假设接受验证。** 品味提出方向，用户证据、运行数据和安全评审决定是否保留。

## 7. 目标产品结构

V1 提议以五项主导航作为基线，并通过任务可发现性测试验证，而不是把入口数量本身作为目标：

| 入口 | 回答的问题 | 主要对象 |
| --- | --- | --- |
| 今天 | 系统是否正常，我需要做什么 | Attention Item、健康摘要、最近变化 |
| 应用 | 谁在使用 AI，拥有什么权限 | Application、Credential、Integration |
| 模型 | 团队可以使用什么，供应是否可靠 | Published Model、Supply、Route |
| 用量 | 使用了多少，花了多少，是否异常 | Usage、Cost、Budget、Saving |
| 团队 | 谁可以管理和使用 | Member、Service Identity、Role |

条件入口：

- 已安装的图片、视频等工作台显示为“工具”，不显示为“插件”。
- 系统设置、扩展管理、审计和高级治理位于管理员菜单，不占一级主导航。
- 面向客户提供服务时，在“应用”中出现客户和集成能力，不新建另一套产品心智。
- SRE、FinOps 等专业角色可固定诊断或治理视图，不被迫经过普通首页。

## 8. 两种用户意图

V1 不再让首次用户理解四个 Profile，而是询问一个业务问题：

> 你准备如何使用 AsterRouter？

| 用户回答 | 产品体验 | 后端兼容映射 |
| --- | --- | --- |
| 为自己或团队使用 AI | 团队网关 | Personal / Enterprise |
| 向客户或其他系统提供 AI 服务 | 服务网关 | Relay Operator / Platform |

第二层问题只在“服务网关”中出现：使用 AsterRouter 管理客户余额，还是连接已有客户与计费系统。它分别映射 Relay Operator 与 Platform。高级安装仍可直接选择现有 Profile。

## 9. V1 成功定义

- 对标准网络和已有 Provider 凭据的新用户，首次受治理调用目标为 P50 小于 10 分钟；复杂审批时间单独统计。
- 首日默认路径无需依赖外部文档，同时专业文档能支持部署、治理和故障恢复。
- 用户不需要理解 Route、Routing Group 和 Provider Account 的区别即可接入。
- 日常操作的 90% 可在“今天、应用、模型、用量”完成。
- 正常运行时首页明确告诉用户“无需处理”；异常时给出影响、建议和可逆动作。
- 任何简化都不降低租户隔离、Secret、幂等、Usage、账务和审计正确性。
- 现有客户升级后数据、Key 和 Gateway API 不变，旧书签有明确迁移落点。

## 11. 决策优先级

本目录定义 V1 产品表面和迁移方向；`docs/goal` 继续定义完整系统目标与工程不变量。当两者冲突时：

- 用户入口、信息架构、文案和交互以本目录为准。
- 安全、数据归属、Gateway、插件、账务和容灾不变量以 `docs/goal` 为准。
- 任何为简化体验而修改 Core 不变量的提案必须单独评审，不能由 UI 重构隐式决定。
