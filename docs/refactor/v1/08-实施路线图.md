# 实施路线图

## 1. 实施原则

V1 是产品表面重构，不是 Core 重写。实施顺序遵循：先建立事实基线，再收敛读取，再承接写入，最后移除兼容 UI。

```text
指标基线 -> 新首页与导航 -> 组合对象与首日闭环
         -> Profile 呈现收敛 -> AsterCloud/插件收敛
         -> 移除旧 UI 兼容路径
```

每个阶段都必须能独立发布、观测和回退。数据库迁移不能成为 UI 回退的前提。

## 2. Phase 0：基线与契约

### 目标

知道当前用户如何完成首次调用，并锁住不能回归的 Core 行为。

### 工作

- 定义 `Time to First Governed Call` 事件和起止口径；
- 记录当前 Setup、Provider、Model、Route、Key 页面漏斗；
- 按首次接入者、管理员、SRE、FinOps 和服务运营者建立任务基线，不用单一平均值覆盖角色差异；
- 记录高级任务的文档查找时间、完成率和事实准确性；
- 建立四个 Profile、主要角色和旧路由清单；
- 为 Gateway、Auth、Policy、Usage、Billing、Job、Artifact、Plugin 建立关键契约测试；
- 定义 Product Facade API Schema 和权限映射；
- 准备新 UI Feature Flag、路由兼容层和匿名重定向计数；
- 建立典型实例 Fixture：全新、小团队、Enterprise、Platform、Relay、离线和大数据量。

### 退出门槛

- 能从事件还原一次真实首次闭环，且分析事件不包含 Secret；
- 关键公开 API 与领域不变量有自动化基线；
- 新 UI 可按用户、实例或环境打开和关闭；
- 当前页面到目标页面全部有处置结论。

## 3. Phase 1：新首页与导航

### 目标

先改变产品的“第一句话”：从资源看板变为行动中心。

### 工作

- 上线 `/home`、五项主导航和管理员菜单；
- 实现 Home 只读投影、最近变化和第一批 Attention Item；
- 统一 `/admin`、`/console`、`/operator`、`/platform` 的管理 Shell；
- 旧首页重定向到 `/home`，保留回退开关；
- 全局搜索支持应用、模型和 request ID；
- 为专业角色验证固定诊断/SLO 视图，不强制共用普通首页路径；
- 建立正常、部分失败、权限和投影延迟状态。

第一批 Attention Item 只选高置信来源：凭据到期、无可用 Route、预算阈值、Usage Sink 积压、插件安全 Advisory。暂不做低价值信号大聚合。

### 退出门槛

- 首页结论与来源事实一致；
- 正常实例不出现无行动价值的事项；
- 事项点击可到达带上下文的现有处理页；
- 旧首页一键回退且不丢配置。

## 4. Phase 2：Application、PublishedModel 与 Onboarding

### 目标

让新用户在一个连续流程中完成首次受治理调用。

### 工作

- 上线 Application 和 PublishedModel 只读投影；
- 新建应用、发布模型、添加供应等场景命令；
- 建立 OnboardingSession、恢复和一次性 Secret 返回；
- 将 Key、Policy 合并进应用详情；
- 将 Route、Account 合并进模型供应详情；
- 上线真实调用检测、示例生成和成功页；
- 对历史 Key 运行只读归属分析，生成整理事项，不自动改数据。

### 发布顺序

1. 影子读取，对比新旧数量、状态和权限；
2. 内部用户启用只读页面；
3. 新实例启用 Onboarding 写入；
4. 小比例现有实例启用新详情；
5. 默认启用，保留旧页面回退。

### 退出门槛

- P50 首次受治理调用低于 10 分钟；
- 重试和恢复不创建重复对象；
- 现有 Key、Endpoint 和模型名不变；
- 新旧页面关键数据差异为零或有批准的口径说明。

### AI 辅助实验

确定性详情页和 Facade 契约稳定后，可以小范围实验只读 AI 诊断：自然语言查询、证据汇总和 Policy 草案。实验不阻塞 V1 核心闭环，也不开放高风险自动执行。只有可复核率、任务时间和误导率达到门槛后，才进入默认体验。

## 5. Phase 3：Profile 产品呈现收敛

### 目标

用户选择使用意图，不选择系统架构。

### 工作

- Setup 改为“团队网关 / 服务网关”业务问题；
- 服务网关再询问外部系统或内置客户管理；
- 保留高级 Profile 选择和后端 Scope 映射；
- Team、Service 两种条件信息架构上线；
- Customer/Portal 委托入口共享新聚合 API；
- 去除重复的 Profile 专属 Provider、Model、Route 页面实现。

### 退出门槛

- 四个 Profile 的后端行为、权限和数据隔离零回归；
- 默认用户无需理解 Profile 即可完成 Setup；
- 服务模式两条路径的 Usage、计费和交付语义清楚；
- 旧 Profile 深链都能解析到新入口。

## 6. Phase 4：插件与 AsterCloud 体验收敛

### 目标

插件成为工具和能力，AsterCloud 只在需要官方服务时出现。

### 工作

- 插件管理迁移到“扩展管理”；
- Contribution 按工作台、Adapter、Widget、Sink 等归位；
- 工作台以“图片工作台”等真实名称进入工具区；
- 统一安装前结果说明、权限差异和数据流展示；
- 将 License、更新、Advisory、Catalog 过期转成 Attention Item；
- 完成在线、断网、离线包、宽限期和撤销体验；
- AsterCloud 链接只在授权、更新、扩展发现和开发者任务出现。

### 退出门槛

- 四个官方插件通过统一 Host、Contribution 与体验验收；
- 禁用/卸载后无残留导航，历史活动仍可解释；
- AsterCloud 断网不影响 Core 数据面和有效本地授权；
- Permission 扩大必须重新批准，Secret 不进入插件前端或目录。

## 7. Phase 5：移除旧 UI 兼容路径

### 前置条件

- 新 UI 默认运行至少两个稳定发布周期；
- 旧路由使用量低于约定阈值；
- 支持工单没有未解决的关键迁移缺口；
- 旧 UI 回退期间未发现 Core 数据兼容问题；
- 发布说明、运维手册和外部集成文档已更新。

### 工作

- 删除重复 Vue 页面、菜单和客户端数据拼装；
- 保留旧路由解析器并返回迁移落点；
- 评估旧 Management API 调用者，逐端点决定保留或废弃；
- 移除 Feature Flag 和双写/影子读代码；
- 固化新信息架构的导航与 Contribution 契约。

### 退出门槛

- 生产构建不再包含旧 UI 主实现；
- 旧书签仍给出明确迁移体验；
- 没有因 UI 删除而删除仍被外部使用的 API；
- 回归、性能、安全和无障碍门槛全部通过。

## 8. 工作流拆分

| 工作流 | 责任 | 主要产出 |
| --- | --- | --- |
| Product Facade | 聚合读取与场景命令 | Home/Application/Model API |
| Experience Shell | 导航、权限、路由兼容 | 统一管理入口 |
| Onboarding | Session、来源、模型、应用、验证 | 首日闭环 |
| Attention | 来源适配、影响、动作 | 行动中心 |
| Migration | 旧路由、归属分析、对比 | 无损升级 |
| Ecosystem | Contribution、Cloud 状态、授权 | 工具与官方服务体验 |
| Quality | 契约、浏览器、安全、性能 | 阶段发布门槛 |

工作流共享 API 契约与设计 Token，但不共享一个巨型前端 Store 或后端 Service。

## 9. Feature Flag 与回退

建议标志：

- `experience_v1_shell`；
- `experience_v1_home`；
- `experience_v1_applications`；
- `experience_v1_models`；
- `experience_v1_onboarding`；
- `experience_v1_ecosystem`。

标志只用于分阶段发布，有明确删除版本。关闭新 UI 时：

- 不回滚或删除 Core 事实；
- Onboarding 已创建对象在旧页面可见；
- 新增 Attention disposition 可保留，无消费者时不影响 Alert；
- 路由解析返回旧页面；
- Facade 可以继续运行供对比，不承接新写入。

## 10. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 聚合模型成为第二事实源 | 稳定根 ID、写入现有领域端口、契约审查 |
| 简化后隐藏生产风险 | L1 结论 + L2 影响 + L3 证据，安全默认 |
| Attention 噪声过多 | 高置信白名单、聚合、有效处理率门槛 |
| 旧 Key 无法归属 | 只读分析、人工整理、不自动撤销 |
| Profile 收敛导致越权 | 服务端 Context、负向权限矩阵、影子对比 |
| 插件破坏统一体验 | 受控 Contribution Slot 和 Design Contract |
| 双 UI 长期存在 | 每个标志设 Owner、指标和删除版本 |
| 首页查询过重 | 专用读模型、新鲜度、分页和性能预算 |
| 克制原则变成固定教条 | 设计假设登记、分角色任务测试、定期复审 |
| AI 建议流畅但不可靠 | 证据链接、类型化命令、误导率门槛、确定性退路 |

## 11. 决策门

每个阶段评审只回答四类问题：

1. 用户是否更快完成同一个结果？
2. 是否减少了必须理解的概念和决策？
3. 是否保持 Core、安全、账务和插件边界？
4. 是否有可度量证据支持进入下一阶段？
5. 这是不能妥协的不变量，还是应该接受推翻的体验假设？

不能用“页面已经开发完成”替代发布完成。指标、兼容和恢复没有通过，阶段就没有结束。
