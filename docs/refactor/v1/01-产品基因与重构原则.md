# 产品基因与重构原则

本文的产品原则已经按 2026 年企业 AI 基础设施场景校准。方法来源、失效条件和不能照搬的结论见 [时代校准与适用边界](./00-时代校准与适用边界.md)。

## 1. 产品基因

AsterRouter 的产品基因不是“管理更多 Provider”，而是：

> 把不稳定、昂贵且充满差异的 AI 供应，变成应用可以长期依赖的一个入口。

这个基因决定了产品竞争力不来自菜单数量，而来自四个用户感受：

- **接入后就不用反复改。** 上游变化不要求业务应用发布。
- **日常不打扰，随时可验证。** 路由、容量、重试和计量在后台正确运行，依据与结果可追溯。
- **出问题时说人话。** 用户知道影响谁、该做什么、动作是否有效。
- **边界可信。** 本地数据、Provider Secret、插件和 AsterCloud 的权限清楚。

## 2. 重构判断

### 2.1 用户购买的是结果

用户不会因为 AsterRouter 有 Provider Account、Model Route、Artifact 和 Outbox 而使用它。用户使用它，是因为：

- 新应用能快速调用 AI；
- Provider 故障不再导致业务临时改代码；
- Key 泄露和越权风险被控制；
- 成本与调用可以解释；
- 图片和视频长任务不再由每个业务重复实现。

所有对外表达都从这些结果出发。内部对象不作为首次学习前提，但在治理、诊断和专业文档中必须完整可见。

### 2.2 简单不是减少能力

企业产品的简单不是把字段删掉，而是减少正常路径中的决策数量。

```text
错误的简单：隐藏限制 -> 用户在生产中踩坑
目标的简单：系统给出安全默认 -> 需要时再解释和调整
```

示例：创建应用时默认生成最小 Scope、合理过期与预算；用户不必先理解每个 Scope，但可以在“高级权限”中查看系统为何这样设置、会影响什么以及如何撤销。

### 2.3 默认值承担责任

V1 默认策略：

- 自动测试 Provider Connection。
- 自动发现模型，并推荐少量稳定模型，不默认发布全部模型。
- 默认以原模型名生成 Published Model，可编辑别名。
- 默认创建 Service 类型 Application 和最小权限 Credential。
- 默认只允许已发布模型。
- 默认启用安全的速率、并发与预算保护，并明确“无限制”的风险。
- 默认选择 `proxy_only` 或场景安全的 Artifact Policy，不静默长期保存内容。

系统无法做出安全判断时，才请求用户选择。涉及扩大权限、数据外发、账务规则和生产可用性的默认值只作为建议，用户确认后才生效。

## 3. 一个核心任务

“首次受治理调用”是 V1 的激活切入点，不是 AsterRouter 全部价值的定义。首次体验围绕以下闭环展开：

```text
Provider connected
  -> model published
  -> application connected
  -> first request succeeded
  -> system guarding
```

以下能力不直接推动该闭环，因此不得阻塞首次使用：组织组、复杂价格规则、插件 License、账单导入、Artifact Sink、多 Region、细粒度报表和高级 Route 策略。

它们可以存在，但不得阻塞标准首次闭环；在企业部署、合规或已有架构要求时，可以从高级安装直接进入。

## 4. 产品表面与系统内核

| 产品表面 | 系统内核 |
| --- | --- |
| 应用 | Gateway Principal + API Key + Policy + Usage Scope |
| 已发布模型 | Gateway Model + Model Routes + Account Mapping |
| 模型来源 | Provider Connection + Provider Accounts + Inventory |
| 活动 | Operation + Attempt + Job + Artifact + Trace |
| 费用 | Usage + Pricing Evaluation + Ledger + Cost |
| 待处理事项 | Alert + Risk + Expiry + Delivery/Job Failure |
| 工具 | Enabled Plugin Contribution + Core Capability |

产品表面是组合和投影，不成为第二事实源。

## 5. 安静的正常状态

系统正常时不制造工作：

- 不用红点提醒用户“有新日志”。
- 不把每次健康检查当成通知。
- 不用 Provider 数、Key 数和插件数制造虚假成就感。
- 不要求用户每日浏览多个 Dashboard。

“安静”有两个前提：健康计算覆盖完整，状态数据仍在新鲜度窗口内。任一前提不成立时，首页只能显示“状态待确认”，不能显示“一切正常”。

首页的理想正常状态：

> 一切正常。3 个应用正在使用 5 个模型，今天没有需要你处理的事项。

用户可以随时展开关键 SLO、监控覆盖、数据新鲜度和最近自动动作。SRE 可以固定诊断视图和订阅明确的 SLO，不受普通首页结构限制。

只有满足以下条件才产生 Attention Item：

1. 需要人做不可自动化的判断；
2. 不处理将在明确时间内影响调用、安全或费用；
3. 系统能说明影响范围和推荐动作；
4. 事项有完成、忽略、延后或自动处理结果。

## 6. 异常不是一张告警表

每个异常必须按用户语言表达：

| 内部信号 | 用户表达 |
| --- | --- |
| Provider Account circuit open | “图像模型的主要来源已暂停，流量正在使用备用来源” |
| No eligible route | “`gpt-image-2` 暂时不可用，两个来源都需要处理” |
| Key expires soon | “订单助手的访问凭据将在 7 天后到期” |
| Budget threshold | “客服助手本月费用已达到预算的 85%” |
| Plugin sidecar crash loop | “视频工作台暂时不能提交新任务” |
| Usage Sink dead letter | “客户平台已有 126 条用量记录尚未送达” |

点击后先显示影响和建议，再显示 Trace、错误码和内部对象。

## 7. 渐进揭示

界面分三级：

### L1：结果

供日常用户使用：今天、应用、模型、用量、团队。

### L2：治理

供管理员按对象深入：权限、预算、模型供应、费用规则、保留策略、集成。

### L3：诊断

供平台工程师和 SRE 使用：Provider Account、Route、Attempt、Trace、Job Event、Plugin Runtime、Audit。

L2/L3 默认不占普通用户主导航；从对应 L1 对象进入，并保留管理员快速入口和全局搜索。SRE、FinOps 和安全角色可以固定高频专业视图，但不由此复制另一套产品。

## 8. 克制规则

新功能在进入 V1 前必须回答：

1. 它服务哪个明确用户？
2. 它推动首次闭环、日常使用还是异常恢复？
3. 用户不配置它时，系统能否给出安全默认？
4. 它是否已有归属页面，为什么需要新一级入口？
5. 它是否把内部对象泄露给了普通用户？
6. 如果六个月无人使用，如何安全移除？

不能回答的问题默认不做。已经实现的功能也要接受复审；若任务数据持续否定其价值，应收敛或移除，而不是用沉没成本保护。

## 9. 语言原则

- 使用“模型来源”，不在普通界面使用 `Provider Connection`。
- 使用“应用访问凭据”，不默认把所有 Credential 都称为 API Key。
- 使用“已发布模型”，不要求用户先理解 Gateway Model。
- 使用“备用来源”和“选择规则”，不首先展示 Model Route 与 Routing Group。
- 使用“活动详情”，把 Operation、Attempt、Job、Artifact 作为不同阶段展示。
- 使用“扩展管理”描述管理员安装行为；安装后的能力按其真实名称出现。

命令、API 和高级诊断继续使用精确工程术语，避免用体验文案污染协议。

## 10. 设计否决项

以下方案默认否决；只有新的用户证据、风险评估和明确 Owner 同时成立时才可例外：

- 再增加一个独立 Profile 或一级管理后台。
- 为每个新 Provider 增加专用主导航页面。
- 在首页增加更多资源统计卡片代替任务闭环。
- 用弹窗教程解释复杂流程，而不改流程本身。
- 让插件自行决定导航分组、权限文案和全局通知。
- 通过默认开启遥测、云端依赖或长期内容保存换取“方便”。
- 同一状态在多个页面提供相互独立的修改入口。
- 让 AI 助手成为核心任务唯一入口，或直接执行未经确认的高风险动作。

## 11. 北极星指标

首要指标：`Time to First Governed Call`，从 Setup 开始到通过 AsterRouter 完成首次带身份、策略、Route、Usage 和 Trace 的成功调用。

辅助指标：

- 首次闭环完成率；
- 无文档完成率；
- 每次闭环的用户决策数；
- 日常任务在 L1 完成的比例；
- Attention Item 的有效处理率；
- Provider 变更时业务应用零改动比例。

页面访问量、配置项数量和插件安装数不作为产品成功指标。

“无文档完成率”只诊断标准首日路径是否自解释，不代表文档越少越好。部署、API、治理和事故恢复还必须分别衡量文档查找时间、任务完成率与事实准确性。
