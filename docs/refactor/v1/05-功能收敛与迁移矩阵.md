# 功能收敛与迁移矩阵

## 1. 分类定义

| 分类 | 含义 |
| --- | --- |
| `KEEP` | 能力和主要体验保留，只统一路径与视觉语言 |
| `MERGE` | 合并进新的业务对象页面，不再独立占据入口 |
| `MOVE` | 移至 L2 治理、L3 诊断或管理员设置 |
| `HIDE` | 仅在意图、权限、数据或能力满足时出现 |
| `REMOVE` | 删除独立 UI 或重复交互；底层能力是否保留单独说明 |

分类针对产品表面，不等于删除后端模型或 API。

## 2. 目标路由

| 目标 | 建议路径 |
| --- | --- |
| 今天 | `/home` |

| 审计 | `/settings/audit` |
| 系统与账户 | `/settings/system`、`/account` |

目标路径不包含 Profile。权限与实例意图由服务端 Context 决定。

## 8. 删除项

V1 明确删除以下重复产品表面：

- Profile 专属的重复 Provider、Model、Route、Plugin 页面实现；
- 首页以资源数量为主的卡片集合；
- Key、Policy、Alert、Trace、Job、Artifact 默认作为一级导航；
- 插件按技术 ID 占据普通用户导航；
- 同一设置在列表弹窗和详情页各自提供独立修改入口；
- Setup 完成后仍要求用户手工串联 Provider、Route、Key 的教程式任务。

删除 UI 不删除对应 Core 事实、审计和兼容 API。

## 9. 路由兼容策略

### 9.1 重定向原则

- 旧 URL 至少跨两个稳定版本保留解析；
- 能确定对象时使用 `301/replace` 式客户端重定向并保留查询条件；
- 需要对象归属时先调用迁移解析器，不按第一个匹配项猜测；
- 无法唯一归属的旧 Key、Policy 深链进入“待整理项”，列出候选对象；
- 重定向记录匿名计数和来源路由，用于决定何时移除兼容层；
- API 路由不随 UI 路由同步改名。

### 9.2 示例

| 旧路径 | 新路径 |
| --- | --- |
| `/admin/dashboard` | `/home` |
| `/console/models` | `/models` |
| `/admin/providers?id=p1` | `/model-sources/p1` |
| `/admin/model-routes?model=m1` | `/models/m1/supply?advanced=1` |
| `/admin/api-keys?id=k1` | 解析所属应用后 `/applications/:id/access?credential=k1` |
| `/platform/usage-sinks` | `/usage/delivery` |
| `/admin/plugins/x/workbench` | `/tools/:resolvedToolId` |

## 10. 数据迁移原则

V1 默认**不迁移业务事实**：

- Profile、Tenant、Principal、Key、Provider、Account、Gateway Model、Route、Policy、Usage 与 Ledger 的 ID 和数据不变；
- `Application` 以 Principal 为稳定根对象组合 Credential、Policy 和 Usage，不复制 Key；
- `PublishedModel` 以 Gateway Model 为稳定根对象投影 Route 和供应状态；
- 无法归属的历史 Key 不自动合并，生成可审计整理事项；
- 旧 Profile 继续决定后端能力与 Scope，前端只隐藏其架构名称；
- Gateway Endpoint、模型公开名和现有凭据在升级后保持可用。

只有新增的 Onboarding Session、用户对 Attention Item 的处理状态和 UI 偏好可以写入新的协调数据。

## 11. 迁移发布门槛

- 新旧页面在同一数据集上的关键数量、状态和权限结果一致；
- 所有旧书签有目标、明确不可用说明或可操作的归属整理页；
- Profile 四种路径和六类角色分别通过权限回归；
- 新 UI 关闭后可以返回旧 UI，不回滚数据库；
- 兼容层移除必须基于旧路由使用量、支持窗口和发布说明，不能按代码整洁度单独决定。
